## `legend-two-counts` — DONE 2026-09-13 (`61c4416`, `563e28e`)

Original text:

> **Legend rules should count entities AND attributes.** [sg] instead of a
> single attribute number on each legend rule, have `N entities ⌄   M
> attributes ⌄` — two counts, each independently expandable. Today each rule
> shows one number (`g.pairs.length`, the attribute count) and one disclosure
> listing the pairs. The entity count is the distinct classes those pairs
> touch, which is the number a reader actually wants when asking "how much of
> the model does this rule decide?". Feeds `one-rule-ownership`, whose
> exception list wants a live site count on each of its ten entries — same
> counting, per exception rather than per rule, and it is what keeps that
> scheme's drift visible after the rule-level counts stop being independently
> derived.

Shipped as specified, plus three things the row did not ask for, all Siggie's
on the day:

- The two counts are two DEPTHS of one list, not two listings. (The first
  implementation built two, which is what made a rule with both open look like
  a list that would not close.)
- Each entity row opens on its own; its `N attributes` badge is the disclosure.
- Cardinality (`0..1`/`1..*`) on every attribute row, replacing a `↠` that
  appeared on multivalued rows only and could not distinguish `0..1` from
  `1..1`.

The feeds-`one-rule-ownership` clause is satisfied: each exception's entities
carry live counts, so the ten entries' drift is visible.
